# HashSomethingOut
The first hash function was poorly designed on purpose. In class, it was said that a loop adding every letter together would not be a very good hash table so I wanted to try it! I did and it was not very good. It was extremely slow compared to the other functions and had a very large number of collisions. The second hash function did surprisingly well! It works similarly to the first function, but adds the value of each character to the power of 2, 3, or 4 depending on if the current hash value modulus three outputs a 0, 1, or 2. It worked much faster than the first function. It had significantly less collisions, too (over 60x less). The third function was one of the best I had made and was the blueprint for the final try function. It held a list of prime numbers and went through each character in the string, using the character value to get a random number from the list. Then it would multiply the current value of the hash product by the prime number. This caused a relatively small number of collisions and unused boxes for a simple hash function. The quote table did a better job with both collisions and unused buckets. The fourth function was not as efficient as the third, but I thought it would be better. It also used a list of prime numbers, but iterated through that list, instead of each character in the string to make each function take the same amount of time. It had significantly more collisions and unused buckets than the third function. As previously stated, the fifth function was based off of the third. I had tried to improve it by increasing the prime number list and adding the found prime index to the hash product of each character of the string to increase randomness, which would hopefully expand as the number multiplied. This increased the efficiency slightly, but not by a lot. 
The first function, which was very inefficient, was shown not only by the massive number of collisions for the title and quote, 92,781,650 and 87,861,178 respectively, but also for the amount of time taken, which was over 9 seconds for both. No other function made for this assignment took over 1.2 seconds to complete. The second function performed significantly better than the first, both having less than 1.5 million collisions and taking around 0.27 and 0.41 seconds to complete for the title and quote tables. This speed increase is likely due to the significantly lower number of collisions. The third function did very well, with only 5557 unused buckets and only hit a bucket with data already inside 5545 times out of 15000 possible times. The quote table took 0.813 seconds while the title table took 0.058 seconds to fill out. This could tell us that the quote strings are significantly longer than the title strings, or that one quote may be very long. The fourth function did not perform as well as the third in terms of unused buckets (7146 and 8658) and in terms of times data reached a bucket with data already in it (7134 and 8646), but was faster, taking slightly over 0.2 seconds for the quote table and 0.074 seconds for the title table. This is because I tried to make this hash function a bit faster by looping around a fixed list, instead of the string, which could be massive, although it still uses the length of the string, making it not O(1). The final function outperformed all others, and was based on the third. It had 5521 and 7026 unused buckets and 5509 and 7014 times where data found data already in its bucket. The quote table took an unusually long amount of time, 1.171 seconds, while the title function took a standard amount of time, that being 0.072 seconds. 
It appears that function 4 was effective if one is prioritizing speed, but that it likely caused less randomness in numbers, causing less efficient statistics in general. The first function was terrible in both ways, likely because inefficient hash functions with linear probing cause a high time complexity, shown by the second function, which increased all stats with the linear probing method. 
As stated, the third and fifth functions were the most effective in terms of limited collisions and unused space. This is likely because it uses multiplication, instead of addition, causing numbers to become significantly larger and amplifying the randomness. If numbers are just added, like in function one or two, those numbers might not scale beyond 15000, causing most of the indexes for the table to be on the low end. Addition also makes it more likely that the final output will be similar. It also helps that every character in the string makes the output more random. In function four, the loop does not depend on the string, making it more consistent, but also less chances for the number to become random. The list of prime numbers also help. Multiplying by a prime number often, but not using the same every time.
